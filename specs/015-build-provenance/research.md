# Research: Signed Build Provenance

All findings were checked on 2026-10-25 (gh 2.102.0).

## R1. Which action signs

- **Decision**: `actions/attest` v4.2.2, pinned at
  `1e69f48acb82d1966a394da916b4c1698aa569d6`, used for all three statements.
  - Called without a predicate, it generates SLSA build provenance v1
    (`https://slsa.dev/provenance/v1`).
  - Called with `sbom-path`, it creates a CycloneDX SBOM attestation
    (`https://cyclonedx.org/bom`).
- **Signing identity**: it signs with the job's OIDC token through Sigstore's public-good Fulcio
  certificate authority and records the entry in the Rekor transparency log. There is no key and
  no secret (FR-003).
- **Storage and output**: it stores the attestation on GitHub as well (the `attestations: write`
  permission), and returns `bundle-path`, the Sigstore bundle v0.3 JSON.
- **Alternatives**:
  - `actions/attest-build-provenance` v4.2.2 and `actions/attest-sbom` v4.1.0 are now thin
    composite wrappers around `actions/attest`. Using them would add two pinned actions for the
    same code.
  - `cosign` with keyless signing gives the same result, but needs an install step and its own
    bundle handling.
  - The SLSA GitHub generator (reusable workflow) gives SLSA level 3 isolation. It changes the
    signer identity to the reusable workflow and adds a second workflow to govern. That is
    disproportionate for a static site, and possible later.

## R2. What the provenance covers

- **The manifest**: the published site is 54 files. Instead of signing 54 subjects, the sign job
  writes a manifest in the standard `sha256sum` format (`<hex>  <path>`, one line per file,
  sorted by path) of exactly the files that go to Pages. It then signs the manifest.
  - A visitor checks any page with standard commands (`curl … | shasum -a 256`, then `grep` the
    manifest).
  - The format is also what `sha256sum -c` reads.
- **Exclusions**: the manifest leaves out itself and the three bundles, which are created after
  it. Everything else in the Pages artifact is listed, the quality report added by the report job
  included.
- **Path**: `/quality/manifest.sha256`, next to the quality report and the SBOM.
- **Three statements per deploy**:
  1. SLSA provenance with the manifest as subject;
  2. SLSA provenance with the SBOM (`quality/sbom.cdx.json`) as subject;
  3. a CycloneDX SBOM attestation with the manifest as subject and the SBOM as content. It says
     "this SBOM describes the build listed in this manifest" (clarification 2026-10-25).
- **Alternative**: passing the manifest as `subject-checksums`, so every file becomes a subject.
  That gives one large bundle and the same assurance, and it still needs the manifest to be
  verifiable on its own.

## R3. Where signing sits in the pipeline, with least privilege

- **Finding**: signing needs `id-token: write` and `attestations: write`. Today Pages is packaged
  in the `report` job, which has `contents: read, actions: read`. Adding the signing permissions
  there would give them to every pull request run of that job too.
- **Decision**: a new job `sign` between `quality-gate` and `deploy`:
  - It runs only for runs on `main` that are not pull requests (the same condition as `deploy`),
    and `needs: quality-gate`, so only a fully gated build is signed.
  - Permissions: `{ contents: read, id-token: write, attestations: write }`.
  - Steps: download the site prepared by `report`, write the manifest, sign three times, copy the
    bundles into `dist/quality/`, verify the attestations, check the files against the manifest,
    and package for Pages.
- **Changes to `report`**: it keeps adding the quality report to the site on `main`. Instead of
  packaging for Pages, it uploads the result as artifact `site`.
- **Changes to `deploy`**: `needs: sign`. Its permissions do not change.
- `quality-gate` is unchanged: on pull requests `sign` is skipped, and the required check keeps
  working.

## R4. How the pipeline verifies before deploying (FR-005, FR-006)

- **Attestations**: `gh attestation verify <file> --bundle <bundle>` with:
  - `--repo SammieEtje/sammieetje.github.io`;
  - `--signer-workflow SammieEtje/sammieetje.github.io/.github/workflows/pipeline.yml`;
  - `--source-ref refs/heads/main`;
  - `--deny-self-hosted-runners`;
  - `--predicate-type` (SLSA for the two provenance statements, CycloneDX for the SBOM
    attestation).

  This checks the Fulcio certificate chain, the Rekor inclusion proof, the signer identity and the
  subject digest against the actual file.
- **Files**: `node scripts/manifest.ts check dist dist/quality/manifest.sha256` re-hashes the tree
  just before packaging. It fails, naming the file, on a changed, missing or unlisted file.
- **Single source**: the verification commands are generated by `src/site/provenance.ts`. The
  pipeline runs them, and the scorecard and README show the same commands to visitors.

## R5. Verification without an account (FR-009)

- **Finding** (tested on a public, attested `cli/cli` release asset):
  - With `GH_TOKEN` unset and an empty `GH_CONFIG_DIR`, `gh attestation verify <file> --bundle
    <bundle> --repo cli/cli` succeeded. Verification needs no login and no GitHub API call.
  - Changing the file by one byte made it fail (exit 1).
- **Caveat**: when output is not a terminal, gh's text format prints nothing on success. The
  instructions therefore rely on the exit code (`&& echo verified`) or use `--format json`.
- **Decision**: the three bundles are published next to the files:
  - `/quality/manifest.sha256.sigstore.json` (provenance of the manifest);
  - `/quality/sbom.cdx.json.sigstore.json` (provenance of the SBOM);
  - `/quality/manifest.sha256.sbom.sigstore.json` (SBOM attestation over the manifest).

  `cosign verify-blob-attestation --bundle … --certificate-identity …
  --certificate-oidc-issuer https://token.actions.githubusercontent.com` is documented as the
  non-GitHub alternative.

## R6. Links on the scorecard and the link check

- **Finding**: the manifest and bundles exist only in the Pages artifact of a `main` run. The local
  build and the `checks` job do not have them, so `linkinator` would report links to them as
  broken.
- **Decision**: the scorecard links to them as usual. The `links` script skips exactly those four
  paths: `/quality/manifest.sha256` and the three `*.sigstore.json` files. The quickstart checks
  them on the live site after the merge.
- **Alternative**: placeholder files in `public/`, as for the quality report. A placeholder manifest
  or bundle would be misleading, because it would fail verification.

## R7. Retention and re-runs

- Attestations stay in Rekor permanently and on GitHub with the repository.
- Each deploy (push, daily run or re-run) signs its own build, and the live bundles always belong
  to the live files.
- Older bundles remain valid for their own files, which are no longer live.
